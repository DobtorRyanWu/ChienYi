# 日後分庫時的客服架構：集中客服資料庫＋API 收單

- 記錄日期：2026-09-23
- 狀態：**已決定方向，尚未實作**。目前只有一個資料庫，本模組照單庫運作。
- 決定：日後每個客戶一個資料庫時，**服務單與問題單集中在自家的「客服資料庫」**；
  各客戶資料庫的前台「意見回饋」**透過 API 把單送到客服資料庫**，不在客戶庫各自處理。

程式裡與此相關的位置都標了 `【分庫】` 註解，搜尋這個字即可找到。

---

## 為什麼要集中

單庫時沒有問題；一旦分庫，若服務單留在各客戶庫：

- 客服要登入每一個客戶庫才看得到全部的單；
- 「多位客戶回報同一問題」要跨庫比對，做不到；
- 統計（各發生功能問題數、各客戶服務單數、每月處理量）只能各庫各算；
- 問題單（S／U／P、時限、改判）本來就是**自家內部**的工作，不該散在客戶庫。

## 目標架構

```
客戶 A 資料庫                 客服資料庫（自家）
┌──────────────┐   API    ┌──────────────────────────────┐
│ 前台意見回饋   │ ───────→ │ 服務單（含來源客戶庫識別）       │
│ （表單、列表、 │ ←─────── │ 問題單、分級、時限、統計          │
│  對話）       │   API    │ 發生功能、類別、處理時限設定      │
└──────────────┘          └──────────────────────────────┘
客戶 B 資料庫 ──┘
```

## 要改的地方（到時的待辦，不是現在）

| 項目 | 單庫（現在） | 分庫後 |
|---|---|---|
| 前台建單 `controllers/portal_feedback.py` `portal_feedback_create` | 本庫 `create()` | 改呼叫客服資料庫的建單 API；附件一併上傳 |
| 前台列表／詳情 | 讀本庫 | 向客服資料庫查「這個客戶庫、這個使用者」的單 |
| 前台對話（chatter） | Odoo 原生 `portal.message_thread` 直接讀寫本庫 | 最難的一塊：留言要雙向同步（客戶留言送到客服庫；客服「傳送訊息」回到客戶前台）。可考慮前台改用自製的對話頁，透過 API 讀寫 |
| 服務單欄位 | — | 新增「來源客戶庫」識別（資料庫名稱或客戶代碼）、來源使用者識別（客戶庫的 user id＋姓名快照） |
| 客戶公司 | 文字欄位 | 可改由來源客戶庫自動帶入（一庫一公司） |
| 工程案件 | 文字欄位（刻意不做 Many2one） | 維持文字；由客戶庫送單時帶入 |
| 類別、發生功能清單 | 本庫主檔 | 只存在客服資料庫；客戶庫前台表單的選項要向客服庫取（或定期同步） |
| 權限 | ACL＋record rule（前台只看自己的） | 客服庫以 API 金鑰辨識是哪個客戶庫送來的；「只看自己的」改由客服庫依來源庫＋使用者過濾 |
| 客服「傳送訊息」防呆 | 後台 JS | 不變（在客服庫） |

## 要先想清楚的問題

1. **API 驗證**：每個客戶庫一把 API 金鑰？金鑰外洩或客戶解約時怎麼撤銷？
2. **客服庫停機時**：前台送單失敗要怎麼辦？（暫存在客戶庫、之後重送？直接顯示失敗請客戶改打電話？）
3. **對話同步**：即時（每次留言都呼叫 API）還是定期同步？客戶端要不要看得到「客服已讀」？
4. **既有資料遷移**：分庫前在單庫累積的服務單，要搬到客服庫並補上「來源客戶庫」。
5. **Email 通知**：目前決定不寄；分庫後若要寄，由客服庫寄。
