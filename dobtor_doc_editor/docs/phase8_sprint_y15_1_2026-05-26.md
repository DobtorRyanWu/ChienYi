## 2. 隱性 bug — Y3 起所有 window keydown listener 全失效

### 2.1 症狀

實測 Y14 ArrowDown：
- `$B press ArrowDown` after opening file menu
- 預期：`.is-focused` class 套到第一個非 disabled item（「重新命名」）
- 實測：完全沒反應

逐層 trace：
1. 加 capture-phase probe listener — fires (count=1) ✓
2. 加 bubble-phase probe listener — does NOT fire (count=0)
3. **結論**：keydown event 從 capture → target → bubble 過程中，某個 listener 在 body→window 之間 `stopPropagation()`

### 2.2 進一步證實 — Y3 Escape 也壞

Sprint Y3 menubar setup 把 `this._onGlobalKey` listener 掛在 `window`：
```js
window.addEventListener('keydown', this._onGlobalKey);
```

裡面有：
```js
if (event.key === 'Escape' && this.state?.openMenu) {
    this.state.openMenu = null;
}
```

**從來沒運作過**。Esc 按下永遠 propagation 被某 capture listener 攔下、_onGlobalKey 不會 fire。menu 只能靠點外面（mousedown 監聽掛在 `document` 上、是 work 的）關。

Y14 鍵盤導航同樣全壞、E2E 沒測到這條 path 所以沒抓出。

### 2.3 三層 probe 確認

```js
document.addEventListener('keydown', () => doc_count++);
document.body.addEventListener('keydown', () => body_count++);
window.addEventListener('keydown', () => win_count++);
$B press Escape
// 結果：doc=1, body=1, window=0
```

**Event 到得了 document 與 body、但到不了 window**。元兇是 Odoo backend WebClient 或 canvas-editor library 在 body 上 capture-phase `stopPropagation`。我們無從 patch、只能把 listener 改掛 document（在 body 之前的層）。

---

## 3. 修法

### 3.1 listener target 從 window 改 document

```diff
- if (typeof window !== 'undefined') {
-     window.addEventListener('keydown', this._onGlobalKey);
- }
+ if (typeof document !== 'undefined') {
+     document.addEventListener('keydown', this._onGlobalKey);
+ }
```

對應 cleanup 也改：
```diff
- window.removeEventListener('keydown', this._onGlobalKey);
+ document.removeEventListener('keydown', this._onGlobalKey);
```

`_onGlobalClick` (mousedown) 本來就掛 `document`、沒事。

### 3.2 額外保險 — mutation 後 `this.render?.()`

window listener 內 OWL useState mutation 理論上會自動觸發 re-render（reactive proxy），但實測時有疑慮，加保險：每個 mutation 點末段集中 `if (dirty) this.render?.()`。實際上改 document listener 後 reactive 也 work 了、`this.render()` 沒必要、但留著零成本、未來別處 reuse 模式更穩。

`_onGlobalClick` 同樣加 `this.render?.()` 保險。

## 6. 教訓

1. **「靜態 audit 全綠」≠「runtime 全綠」**：Y15 純 grep handler 都存在、看不出 listener 掛錯地方。runtime crawl 比 code review 找得到更多隱性 bug。下次 sprint 不能只靠靜態審計、要真連 browser 跑過幾條 path。
2. **`stopPropagation` 在 capture-phase 是 listener 殺手**：Odoo backend / canvas-editor 把鍵盤 event 在 body 上 capture-phase 攔下、window listener 永遠收不到。修法不是「不要 stopPropagation」（那層是 framework / lib 不能改）、而是「listener 掛到比 body 更上層的 document」。Sprint Y4 教訓「synthetic KeyboardEvent doesn't fire window listeners」其實也是這個問題的子集 — 早該套用到既有 window listener、結果 5 個 sprint 都沒動到。
3. **probe 三層比 console.log 高效**：當 event 不到、原因可能在任何一層、用 capture-probe + bubble-probe + intermediate-target-probe 一次定位、不用反覆改 code 跑 debug。
4. **`this.render?.()` 不傷身、可當保險**：OWL 18 reactive proxy 在 window listener context 內**是**會 schedule re-render（修了 listener 後 mutation 自己就生效、`this.render()` 沒被觸發到）。但保留呼叫零成本、`?.()` optional chaining 在 unmount 後安全。Pattern 留著未來碰其他 framework 也好用。
5. **bug 沒被 E2E 抓出 = E2E 沒測這條 path**：G.1/HN.1/J.1 全用 mouse click + 寫 input、沒按 ↑↓ 鍵盤導航、沒按 Esc 關 menu。下次新功能擴 E2E 要記得 user-driven path 兩條 — mouse 與 keyboard。
