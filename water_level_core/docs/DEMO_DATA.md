# 磺港溪示範水位資料

> 建立於 2026-08-31，2026-09-07 加入工地站。資料庫 `odoo18_dev`，工程案件 **43（HGX-A）**，
> 場域「磺港溪（延壽橋至三合橋）」（code `HGX-WRA`，**別改 code**，兩支工具靠它找場域）。
> 相關工具在 `tools/water_level_demo/`。

真實水位計還沒有資料進來，但 DM 與客戶展示需要看到「水位在動」。
這份資料讓系統現在就能演示完整的水位監測流程。

## 哪些是真的，哪些是合成的

| 期間 | 來源 | 筆數 | 序號 |
|---|---|---|---|
| 2025 全年 | **水利署實測值** | 154,312 | 無（來源本來就沒有流水號） |
| 2026-01-01 起 | **系統合成**，不是量測值 | 每站每 10 分鐘一筆 | 有（模擬設備會給） |

分界點很好認：**有流水號的就是合成的**。

四個站，由上游至下游：

| 上下游序 | 設備碼 | 站 | 角色 | 資料怎麼來 |
|---|---|---|---|---|
| 10 | `WL-HGX-060` | 薇閣(060) | 水利署流域測站 | 自己的 2025 年實測 + 合成 |
| 20 | `WL-HGX-403` | 中和橋(403) | 水利署流域測站 | 同上 |
| 30 | `WL-HGX-601` | 分洪入口(601) | 水利署流域測站 | 同上 |
| 40 | `WL-HGX-A01` | **C 段工區** | **工地自己的設備** | 向 601 借形狀（見下節） |

前三站是**外部公開資料來源**（流域上游的參考站）；`WL-HGX-A01` 是 DM 的 S25 講的那個主角
——工地現場自己的水位計。場域的「代表監測站」設成它，前台水情頁一打開預設就顯示它。

場域、監測站與資料來源都打了「示範資料」勾，後台表單右上角有橘色緞帶。

## 工地站怎麼借水利署的資料

`WL-HGX-A01` 沒有自己的歷史真值，它的**水文形狀整份借自分洪入口(601)**
（`demo_baseline_device_id` 指向它）：洪峰長什麼樣、枯水期多平、哪個月容易下雨、
讀數多常不動，全部是水利署實測資料的統計特徵，不是憑空造的曲線。

**借的是哪幾層很重要**。合成器的亂數分成三層，借用時只有最後一層是各自獨立的：

| 層 | 種子 | 借用的站怎麼處理 |
|---|---|---|
| 季節基線（重播去年同時刻的真值） | 母本站的歷史 | 跟著母本 |
| 事件層（雨型觸發、每日錨點） | `shape_uid` | **跟著母本** |
| 每 10 分鐘的抖動與黏滯 | `device_uid` | **各自獨立**（那是量測雜訊） |

第二層一開始寫錯過：事件層原本也用 `device_uid`，結果兩站**各下各的雨**——
相距 34 公尺卻只有 0.50 的相關係數，十一場暴漲有七場只有一站在漲，
還出現「工地站告警、上游 34 公尺的測站一切正常」連續 25 小時。
真實的相鄰測站幾乎同漲同退。改用 `shape_uid` 之後相關係數升到 **0.944**，
三場暴漲全部兩站同漲（漲幅 0.69/0.69、0.70/0.74、0.82/0.83），
只有工地站告警的時間格 **歸零**。

兩站相距約 34 公尺（工地在下游），依河道坡降估算水面高差 **0.20 公尺**，
填在工地站的**基準高程**（`datum_elevation = -0.20`）。

**為什麼高程差要走 `datum_elevation` 而不是另造欄位**：`ingest_readings()` 寫入時做的
就是 `value = raw + datum_elevation` 並原樣保留 `raw_value`，而合成器的基線、初始值、
夾限、雨型上限、手動暴漲目標值全部在 raw 域運作。所以只要設 `datum_elevation`，
合成器內部從頭到尾留在母本站的值域、夾限自動對齊，`demo_profile` 整份複製、
一個欄位都不用調，唯一的平移發生在寫入那一步。

驗證（2026-09-07 實測）：工地站 raw 的值域與 601 同期完全重疊（平均只差 0.01 ——
兩站各有獨立的隨機偏移，不是複製貼上），value 則整體低 0.20。

警戒 **11.10 / 11.40 / 11.70**，由母本警戒平移同樣的高差自動算出，不是寫死的數字。
工地站水位中位數約 10.4，距三級警戒 0.7 公尺，平時不會誤報。

**工地站有自己的資料來源**（「示範資料合成器（A 標工地）」）。手動觸發暴漲的旗標是掛在
資料來源上的，四台共用一個來源會變成按一次鈕四站一起漲；分開之後按工地站的鈕
只有工地站淹水（實測峰值 11.80，越過一級警戒——洪峰是疊在當時的基線上，
所以實際峰值會比設定的目標再高一些）。

## 已知的不精確（不要當成事實引用）

1. **座標是概略值**。來源截圖的地圖標記三站都落在同一點，那是地圖預設中心不是站址，
   無法回推。待水利署提供。
2. **三級警戒水位是推定的暫定值**，依歷史分位數估算，**不是水利署核定值**：
   薇閣 7.0/7.3/7.6、中和橋 12.8/13.0/13.2、分洪入口 11.3/11.6/11.9（公尺）。
3. **時間**：來源檔沒有時區標記，依水利署網站慣例當作台北時間轉存 UTC。
   對照點：台北 `2025-01-01 00:00` = 資料庫 `2024-12-31 16:00`。
4. 中和橋原始資料有 76 筆 `0.000`（2025-04-27 起的設備故障值），匯入時剔除。
5. 分洪入口全年有 1,985 個時間格子沒有資料——那是水利署設備的真實漏測，不是我們漏收。
6. **工地站的座標與高程差都是估算值。** 座標取自 memory 記載的 A 標預設 GPS，
   高程差是用兩站座標距離乘河道坡降 1/150 估的。真正的斷面高程要現場測量。
   警戒值同樣是推定——工地警戒的真正依據應該是工區地面高程，那個數字目前沒有。
7. **分洪入口的時間戳被對齊到 10 分鐘格子，最多早 9 分鐘。** 那一站的取樣時刻會漂移
   （分鐘個位數 0~9 均勻分布，例如 `14:03`、`14:13`），而序號是用時間格子算的，
   所以匯入時一律下捨到格子起點（`14:03` → `14:00`）。**水位值本身完全正確**，
   只有時間戳失去了分鐘級精度。薇閣與中和橋原本就對齊在整十分，不受影響。
   要拿這一站做分鐘級的精確分析時要知道這件事。
8. 三站真的會在十分鐘內暴漲一公尺（薇閣 2025-12-09 單格 +1.53 m）。
   看到合成資料陡升先查歷史，不要當成 bug——用抽樣算出來的「最大變化」會嚴重低估這種事件。

## 每 15 分鐘怎麼更新的

排程「水位監測：從資料來源撈取」每 15 分鐘跑一次，向資料來源
**示範資料合成器（磺港溪）** 要資料。合成器不連任何外部系統，
它拿「基線年（2025）同月同日同時分」的真值當底，疊上均值回歸的隨機偏移，
產生從「這台最後一筆之後」到現在為止缺的每一個 10 分鐘格子。

合成邏輯在 `models/demo_synth.py`，設計理由寫在該檔的 docstring。
一句話版本：**真實感測器有 44~85% 的時間讀數完全不動**，
少了這個「黏滯」，合成序列每一步都在抖，一眼就是假的。

其餘幾件事沒做會在展示時被看出來，都寫在程式碼註解裡：
雨型要照歷史的季節分布走（否則颱風季一場雨都沒有、二月卻有洪峰）、
基線有洞時不能拿前一個輸出值頂替（會讓水位一路漂到歷史最高值並平頂數十小時）、
跨年重播的落差要指數收斂而不是等速爬、洪峰要在撞到上限前按比例縮小（否則峰頂被削平）。

**可重現性**：亂數全由 `(設備碼, 時間格子)` 決定、偏移量每天重新錨定，
所以清掉重生會得到同一批數字。實測兩站 × 三種起點（從頭、從中段、只重算最後 400 格）
各 400 格全部相同、最大差 0.000 m。

### 擬真度是量出來的，不是看出來的

`tools/water_level_demo/verify_demo.py` 拿合成序列與同月份的歷史真值比五項統計：

| 指標 | 門檻 | 2026-09-07 實測（薇閣 / 中和橋 / 分洪入口 / **工區**） |
|---|---|---|
| 平均值 | 差 ≤ 0.02 m | 0.000 / 0.001 / 0.003 / **0.015** |
| 零變化比例 | 差 ≤ 10 個百分點 | 6.4 / 3.6 / 0.9 / **3.5** |
| \|Δ\| p95 | ≤ 歷史 1.5 倍 | 1.50 / 1.00 / 1.00 / **1.00** |
| 月度極值 | ≤ 歷史**同月**最大 + 0.3 m | +0.05 / +0.06 / +0.18 / **+0.04** |
| 標準差 | 歷史的 0.5 ~ 2.0 倍 | 1.00 / 1.43 / 1.00 / **1.25** |
| 跨站相關 | 借用的站與母本 r 在 0.90 ~ 0.9995 | — / — / — / **0.944** |
| 基準高程 | `median(value − raw)` 等於設定值 | 0.00 / 0.00 / 0.00 / **−0.20** |

工區那一欄比的是**分洪入口的歷史**（它沒有自己的歷史），對照關係寫在
`verify_demo.py` 的 `STATIONS` 表裡。標準差改成雙邊界是有原因的：
基線借用若失敗，合成器會退回中位數 fallback、變成一條幾乎不動的線，
而所有「≤ 歷史 N 倍」的上界判準對這種失敗全部照過。

**跨站相關那一項是後來補的，而它補的正是前面五項全部漏掉的東西**：
那五項都是各站自己的邊際統計，沒有任何一項把兩站放上同一條時間軸。
所以「事件層沒借到、兩站各下各的雨」那個問題，五項統計全部 PASS 也照樣看不出來。
上界 0.9995 是防另一個方向的失敗——高到接近 1 就變成同一條線平移，
量測雜訊本來就該獨立。

改了任何合成參數就重跑這支，它會直接判 ACCEPT / REJECT。

**這支工具自己踩過兩個坑，都已修掉**，看它的 docstring：
① 原本比的是「不超出歷史**全年**值域」——但合成器的夾限用的就是同一組數字，
這一項在數學上永遠會過，等於沒開。改成比同月份極值之後，立刻抓到分洪入口
一月冒出一場只有豐水期才有的洪峰。
② 原本把十萬列走 `docker exec` 的 stdout 撈回來算，那條路徑會靜默截斷
（本環境已知問題），實測發生過整站資料消失、退出碼仍是 0，然後拿不完整的序列算出
PASS。現在統計全部下推到 SQL 算，另外加了筆數守衛。

## 展示告警

三站服務等級是 **flagship**（旗艦），即時告警才會啟用。

- **手動觸發**：資料來源表單上的「手動觸發暴漲」按鈕。按下去之後，
  下一輪撈取（最多 15 分鐘）開始漲水，越過三級警戒後自動退水。
  想立刻看到就再按「立刻撈一次」。
- **自動**：每天 5% 機率自己下一場雨（約三週一場）。這個機率不是隨便設的——
  設 0.3 時八個月累積下來會把整體標準差墊高到歷史的 3.2 倍，合成資料就不像真的了。

告警事件報表（`report/water_level_event_report.xml`）對示範站會在最上面印一段警語，
借用基線的站另外說明「設備上報值」欄位其實是向誰借的。
那份報表長得像證據，沒有標記會被當真。

> ⚠️ **旗艦等級會把告警送到「告警外送通道」設定的端點。**
> 建立這份示範資料時 `odoo18_dev` 的通道是 **0 筆**，所以不會有東西送出去。
> 之後若有人在這個資料庫建了外送通道，示範資料的假告警**會真的被送出去**——
> 為此外送的 JSON 帶了 `is_demo` 欄位，收端至少分得出來這不是真的水位事件。
> 這條路徑不必按按鈕也會走：撈取排程一停，三台示範設備會轉成斷線並開 critical 事件。

## 前台會怎麼顯示

`/construction/43/water-level` 頁面頂端有一條橘色的「示範資料」橫幅，
明講這個工程的水位是系統模擬的。**這一條不能拿掉**——後台的緞帶只有內部人員看得到，
而這個頁面業主也看得到；一條沒有但書的水位曲線加上「剛剛更新」，會被當成真的。

## 要展示「缺號偵測」

合成資料的序號是連續的，所以平常不會有缺口。要演示的話，刪掉幾筆再跑一次缺口稽核：
系統會抓到那段序號不見了。這是真的偵測，不是預先埋的假資料。

## 重來與清除

```bash
# 只清合成讀數，保留水利署歷史真值（調完合成參數要重生時用）
docker exec -i -e WL_PURGE_MODE=synthetic -e WL_PURGE_CONFIRM=YES \
    odoo18 odoo shell -c /etc/odoo/odoo.conf -d odoo18_dev --no-http \
    < tools/water_level_demo/purge_demo.py

# 全部清掉：讀數、監測站、場域、資料來源
docker exec -i -e WL_PURGE_MODE=all -e WL_PURGE_CONFIRM=YES ... < .../purge_demo.py
```

水位紀錄是純追加式資料（`unlink()` 擋、資料庫 trigger 也擋），
清除腳本會在同一個交易內開維護視窗——這是刻意的門檻，不是障礙。

清完到重新載入之間，監測站的最後上報時間會退回 2025 年，
告警排程（每 5 分鐘）會把三站判成斷線並開 critical 事件。
資料補回來之後**那些事件不會自己關**（水位事件沒有自動關閉機制），
要到後台「品質安全 › 水位監測 › 水位事件」手動關掉。

> ⚠️ **「只清合成讀數」的判準是「這筆有沒有序號」，不是「這筆是不是合成的」**——
> 資料表上分不出這兩件事，真水位計上報的讀數同樣帶序號。
> 所以腳本會先檢查這些站是不是還接著示範合成器，一旦切換到真來源就拒絕執行。
> 換到真設備之後要清舊資料，請人工確認範圍，不要靠這支腳本。

## 真設備接上以後

把資料來源的「來源型態」從「示範資料合成器」改成 `postgres` 或 `http_json`，
填上連線資訊與欄位對應即可。監測站、歷史資料、前台頁面、告警設定全部不動——
`water.level.source` 這一層的存在就是為了這一刻。

換過去之前記得先清掉合成讀數（`WL_PURGE_MODE=synthetic`），
否則真假資料會混在同一條時間線上。
